# Phase 2 Todo：完整编码循环、测试与 PR 人审

> 目标：在 Phase 1 的单仓库低风险修改基础上，形成可审阅的远程研发闭环：
> **创建任务 → 多轮编码与测试 → 创建分支 → 提交变更 → 推送远程 → 生成 PR → 人工审批 → 记录结果**。

## Phase 2 范围

### 纳入

- 一个任务对应一个远程代码变更流程
- 多轮代码检索、修改、测试和修复
- 任务分支、提交信息和变更摘要
- GitHub 或 GitLab 之一的 PR/MR 创建能力，保留 Provider 抽象
- PR 描述、测试结果和风险信息自动生成
- PR 创建前后的人工审批节点
- Desktop 端任务详情、编码循环、测试结果和 PR 人审工作台
- 持久化任务状态、审计轨迹和可恢复检查点
- 真实 API、集成测试和可重复演示流程

### 暂不纳入

- CI/CD 触发、流水线日志解析和自动修复 CI 失败
- 自动处理复杂合并冲突和跨分支迁移
- 多仓库任务和跨仓库 PR
- 生产环境操作、强制推送和远程分支删除
- 自动合并 PR
- 大规模迁移、完整语义向量库和复杂调用图

## 交付节奏

建议周期：3–4 周。

| 周期 | 目标 | 可演示结果 |
|---|---|---|
| 第 1 周 | 编码循环、任务状态和分支隔离 | 一个任务可以连续完成检索、修改、测试和修复 |
| 第 2 周 | Git 提交、远程 Provider 和 PR 草稿 | 变更可以推送到任务分支并生成可审阅 PR |
| 第 3 周 | 人审、审计、恢复和 Desktop 联调 | 用户可以批准、拒绝或返回修改，并恢复任务 |
| 第 4 周 | 集成测试、演示和发布门槛 | 完成一条可重复的 Issue 到 PR 演示流程 |

## Phase 2 完成定义

以下场景全部成功，Phase 2 才算完成：

1. 用户在 Desktop 中选择一个已注册的 Git 仓库并创建任务。
2. 系统创建隔离的任务分支，并记录任务开始时的工作区状态。
3. Agent 完成至少一轮代码修改并生成可审阅 diff。
4. 用户确认后应用修改，系统运行单项测试和项目测试。
5. 测试失败时，系统定位失败并生成下一轮修复计划。
6. 修复后测试通过，系统展示全部轮次和最终 diff。
7. 用户批准提交和推送，系统生成任务分支上的提交。
8. 用户批准创建 Draft PR，系统生成 PR 描述并返回远程 URL。
9. Desktop 展示 PR 状态、提交 SHA、测试结果、审批历史和完整审计轨迹。
10. 在网络失败、测试失败或服务重启后，用户可以恢复或取消任务，不会产生重复提交或重复 PR。

## Phase 2 风险控制

- 默认只允许创建和推送任务分支，不允许强制推送、删除分支或写入受保护分支。
- 默认创建 Draft PR，不自动合并，不自动关闭 Issue。
- 分支、提交、推送和 PR 创建均必须经过对应人工审批。
- 每次远程写操作必须具备幂等键、审计事件和可查询结果。
- 测试失败、预算耗尽、连续修复失败和高风险 diff 必须转人工。
- 所有凭据通过环境变量或安全存储注入，禁止进入日志、数据库、Patch、Commit 或 PR 文本。
- 远程调用只允许配置的 Provider 和仓库，禁止任意 URL 请求。
- 任何服务重启恢复都必须显式标记为“需恢复”或“需人工确认”，不能静默继续执行。
